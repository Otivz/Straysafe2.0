## Intent

Make pet registration the foundation of the Resident Lost Pet workflow without ever delaying an urgent report. A Lost Pet report is now about one of the resident's own registered pets; registration is a prerequisite, not ownership verification, and it is never required for any other kind of report. The earlier wording that called pet registration voluntary, and the Lost Pet form that let a resident type the pet's details, contradicted that and were replaced.

## Key changes

**Backend (every rule in one module, used by every route)**

- `backend/app/utils/lost_pet_rules.py` (new): a resident's Lost Pet report must name their own registered, active pet (`403` staff, `422` register first, `404` not theirs, `409` inactive); one active lost report per pet (`409` with `{"code": "LOST_REPORT_EXISTS", "report_id": N}`), where "active" is `case_state.is_closed` (not `pets.status`) and the check reads with `SELECT ... FOR UPDATE` on the pet and on its reports, so two simultaneous requests are serialised on MySQL; no re-categorising a report into or out of Lost Pet; a pet with an open lost report cannot be archived, merged or deleted; reopening is refused while another report of the pet is open; the animal's details on the report come from the pet record; the pet and the last-seen details are frozen into a server-made snapshot.
- `backend/app/routes/reports.py`, `backend/app/schemas/report.py`: the rules above on create and update; owner ids, the Leader's verification flags, the legacy `[LOST PET REPORT]` marker and any pet facts from the browser are dropped or refused; `ReportCreate.last_seen_at` (optional, never in the future).
- `backend/app/routes/lost_pet_alerts.py`: a notice needs a Lost Pet report; a resident asks for it for their own pet's report, a Leader may still prepare one for an older report with no pet.
- `backend/app/routes/pets.py`, `backend/app/utils/pet_ownership.py`: Dog or Cat only (clean `400`); a resident cannot set the owner, who registered a record, `is_verified` or the status, and photo addresses must be the subdivision's own uploads; `GET /pets/subdivision/{id}` is scoped to the subdivision; the Leader-assisted link: `POST /pets/{id}/assign-owner` now needs an evidence note (at least 10 characters) from a Leader, asks the resident to confirm (the usual owner confirmation, ownership does not move before they accept) and keeps how the Leader checked in the pet's history.
- `backend/app/utils/identity_decision.py` (new), `backend/app/services/case_lifecycle.py`, `case_summaries.py`, `case_view.py`: `identity.decided` / `identity_decided` keeps "linked by the reporter" apart from "identity confirmed by a Leader" (a report that names a pet is stored as identified by the status sync, so a Leader's own decision is recorded as a `CASE_IDENTITY_DECIDED` audit line); `GET /cases/{id}` returns a `pet` block (registry now, as reported, owner and emergency contact, last seen as filed and as in the notice, removed and restricted states), scoped to the viewer's subdivision.

**Schema (smallest compatible change, mechanism confirmed first)**

- There is no Alembic. A schema change is a model attribute, an entry in `REPORT_COLUMNS` in `backend/app/db_migrations/case_alignment.py` (added with the other missing columns in one `ALTER TABLE`, checked by `check_case_schema`, run at import of `main.py`), the canonical snapshot and its `.txt` copy, and `DATABASE_SCHEMA.md`. The live database was not touched or rebuilt: it gets the column at the next backend start.

**Left as they were, and stakeholder-policy items not decided here**

- Species beyond Dog and Cat (the MySQL `pets.pet_type` enum needs a migration and the stakeholders' confirmation). One registered owner per pet: no household co-owners.
- Whether the subdivision itself obliges every pet owner to register (proposal A3) is still open; the application requires registration only for a Lost Pet report.
- Who may link an office-entered record: the existing rule was kept (the staff member who entered it, or the Administrator). Whether other Leaders of the same subdivision should be able to is a policy question.
- `GET /pets/` for a Leader still lists ownerless records with no registrant across subdivisions (the Leader app uses the scoped list). `pets.is_verified` is stored and shown as not verified; nothing sets it.
- The row locks are a MySQL behaviour: SQLite has none, so the test proves the lock is requested, not the race. The first backend start after this change runs `ALTER TABLE reports ADD COLUMN pet_snapshot JSON NULL` (a failed required column stops the application, by design).
