## Intent

The approved Admin and Resident previews were complete, the database and backend alignment was done and the database safety correction validated. This change connects those interfaces to the existing backend, with real data and real actions instead of sample ones, without redesigning anything, without retiring the legacy portals, without switching production routing, without changing the schema or running a migration, and without touching the configured database.

## Key changes

### Three ways to run the screens (nothing existing moved)

| Mode | Where | Data |
|---|---|---|
| Legacy portals | every existing route | the real API, unchanged, still the default |
| Preview | `/admin-preview`, `/resident-preview` | sample data in the browser; written inline as `import.meta.env.DEV` in `frontend/src/main.tsx`, so a production build drops the chunks and the sample accounts |
| **Live** (new) | `/subd-admin` (Subdivision Leader, role 2), `/resident-app` (resident, role 1) | the real API; mounted in development builds, and in a production build only when it sets `VITE_NEW_UI=true` |

The live bases start with `/subd` and `/resident` on purpose, so the existing token-key rule in `utils/api.ts` and the 8-hour staff idle rule apply unchanged. One set of screens serves both entries through a `mode` object (`admin/mode.ts`, `resident/mode.ts`): the shared screens never import a mode's code, which is what keeps sample credentials, seed data and simulation tools out of the live chunk. `frontend/vite.config.ts` gained one optional environment variable, `STRAYSAFE_API_TARGET`, for where the dev server forwards `/api` (default unchanged: port 8000); the browser tests use it.

### Authentication (the existing contract, nothing new)

`admin/auth/httpGateway.ts` and `resident/auth/httpGateway.ts` use `POST /auth/login` (email only), the session storage the legacy sign-ins use, the shared client's refresh cookie, `GET /auth/verify-session`, the resident OTP flow (`POST /users/`, `/auth/verify-otp`, `/auth/resend-otp`), the emailed-code password recovery, and `logoutUser()`. A role that signs in at the wrong address is refused and the session the server opened is revoked. Changing a password ends every session and the screens say so. No endpoint and no authentication system was invented.

### The data layer (Admin and Resident)

`admin/live/*` and `resident/live/*` (api, adapters, actions, provider) keep the preview provider's contract and add what a server needs: summaries first and detail on demand (`GET /cases/summaries`, `GET /cases/work-queue`, `GET /reports/?mine=true`; a case or report is read in full when it is opened), no optimistic updates (every action is one or a few requests and the provider re-reads what it touched), `issues` and `loadError` instead of silent fallbacks, a `capabilities` object that turns off, with a reason, what the backend cannot do, typed errors (`network`, `session`, `server`) carrying the server's own sentence, naive server times read as local wall-clock time (`live/dates.ts`, as the legacy screens do), case references `SS-<year>-<id>`, and privacy taken from the server (`redact_response`). A refresh that fails after a saved change never turns the change into an error. There is no fallback to sample data in live mode. The tables of screen action to request are in `docs/01-system/NEW_INTERFACES_INTEGRATION.md`.

### Backend additions (additive; no schema change; no migration run)

`GET /cases/summaries` (paged, filtered, scoped); `GET /cases/work-queue`; `GET/POST /cases/{id}/notes` (stored as audit-log rows); `POST /cases/{id}/warnings/{wid}/observations`; the `office` block of the case settings; `category_id`, `subdivision`, `publication` and `stored_categories` in `GET /cases/categories`; `GET /reports/?mine=true`; `case_outcome` on a report (neutral wording); `GET /ownership-claims/mine` and `POST /ownership-claims/{id}/info`; `GET /lost-pet-alerts/mine` and `/all`, and `requested_by` on a notice (never shown to neighbours). New services: `case_summaries.py`, `case_compliance.py`. Documented in `docs/01-system/CASE_WORKFLOW_BACKEND.md`.

### Found and fixed during validation

The browser run, on a database shaped like the real one, found problems the unit tests and the first fixtures had hidden:

1. **The resident timeline never showed "Report received".** The server lists a report's history oldest first; the adapter assumed newest first. It now recognises the original submission by what it says, and the unit test uses the server's real order.
2. **The Admin timeline would have shown the original submission twice** (its own line plus the server's). It is shown once.
3. **The resident screens promised "your notice is live" whatever the subdivision's setting.** The server publishes a lost-pet or found-animal notice at once or holds it for review, separately for each kind (default: review). The report screens now read the setting (`publication`) and word the first step, the review step, the consent box and the confirmation to match; after sending, the confirmation follows what the server actually did.
4. **Older-category reports would have been labelled "Other animal concern".** A report keeps the category it was filed under (Injured, Aggressive, Rabies Risk, Roaming Animal, Rescue Needed), which the server already reads as a kind. `stored_categories` hands that mapping to the resident screens.
5. **The Admin case maps drew the sample reporting area.** The connected Admin now reads the server's (`GET /reports/coverage-area`) and says so if it cannot; the sample landmarks stay in the preview.
6. **The resident welcome line named the sample subdivision** to every visitor. It is neutral until someone has signed in.
7. **The resident profile edit carried the sample street list** (the sign-up screen already typed the street in the connected app) and said "in the real app, changing your email asks you to verify the new address", which the server does not do. The street is typed and the hint is accurate when connected; the preview is unchanged.
8. **The claim dialog told the Leader that accepting a claim confirms ownership.** The server deliberately does not (an existing, tested rule: the claim is marked accepted and the case's ownership stays "under review" until the Leader records that decision, with evidence, on the Assessment tab). A new capability, `acceptConfirmsOwnership` (on in the preview, off when connected), makes the dialog and the claims panel say what the server does.
9. The test database numbered the report categories from 1, so a lost-pet report filed through the app was not recognised as one (older backend code looks a Lost Pet report up by category id 6, which the real schema script gives it), and SQLite stamped rows in UTC while MySQL stamps local time. The test server now numbers the categories like the schema script and stamps local time. This is a **deployment fact**, not a fix: see the risks below.

## Remaining risks and decisions

1. **No conversation view in the new Admin.** A resident's "add information" is posted to the case chat; the new Admin cannot read it, so a Leader who only uses the new screens would miss it (the legacy Messages page still shows it). Add a panel (a small read, `GET /chat/reports/{id}/messages`, and a design) or keep the legacy page open beside the new Admin. Not a problem for a pilot with the legacy portal reachable.
2. **Functions only the legacy portals have:** the pet QR card and scan history, the owner's observation updates after a warning, lost-pet match review, manual matching, the hazard-alert page, removed pet records, and the system administrator's portal (role 4, never in scope). Redirecting the old entry routes would strand them; each needs a decision (keep, build, retire).
3. **Not run on a real engine.** The new SQL is plain and expected to behave the same on MySQL, but only SQLite ran. Run the journey on a staging MySQL copy with test data first, and check three facts there: the category named "Lost Pet" has id 6; the database server's time zone is the subdivision's (the screens read stored times as the device's local time, like the legacy screens); photo uploads and emailed codes work with the configuration the legacy screens use (they were read, not run).
4. **The reporter's timeline shows the server's own lines,** including warning and observation lines such as "WARNING ISSUED: Official 1st Warning ..." (the server already removes residents' names from them). The legacy API sends the same lines. Decide whether a reporter should see warning lines at all; it would be a server-side filter.
5. **Capability gaps the screens state plainly** (listed in `NEW_INTERFACES_INTEGRATION.md`): accepting an ownership claim does not confirm ownership (the server's rule, now worded as such); the Admin cannot suspend or verify accounts, edit the position title or the subdivision identity, record per-pet match decisions, choose a warning's delivery or start, or write a notice without a case; the Resident cannot message the office, switch community notices and advisories separately, receive text messages or report without a pinned position.
6. **Before a Leader can use warnings,** the subdivision must confirm a policy; the office profile must be filled in for residents to see it; the publication settings decide what residents are told.
7. **Recommended reviews before a wider rollout,** with evidence and the command: `npx @ghostbyte/agent-docs-kit@latest security worksheet api-layer` (why: new read endpoints and the resident privacy allow-list; evidence: `test_resident_live_api.py` and `test_case_notes_queue.py` plus a read of `report_visibility.py`) and `npx @ghostbyte/agent-docs-kit@latest engineering worksheet testing-types` (why: the browser journey and its isolated API are now test infrastructure the release depends on). Neither was run or claimed.

8. **The computer's disk filled up during the last regression run** (about 3 MB free of 240 GB; about 29 MB after clearing three of my own scratch items). About 3.4 GB of it is throwaway data in the temp folder left by test tooling used during this work: `sa-cdp-*` browser profiles (about 3 GB) from the scratch test harness, `straysafe-live-test-*` profiles (about 0.3 GB) from runs of the new browser test that were cut short, and `straysafe-test-*` throwaway databases (about 0.1 GB) that `backend/tests/_isolated_db.py` creates for every backend test run and never removes. A sweep of that folder was not permitted in the session, so it was left alone; the three suites named above need one more run after it is cleaned. Worth a follow-up: have `_isolated_db.py` remove its folder when the process ends.
