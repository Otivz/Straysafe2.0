## How the schema changes today

There is no Alembic or other versioned migration tool. A schema change touches four places:

1. **The model** in `backend/app/models/`. `Base.metadata.create_all(bind=engine)` in `main.py` creates tables that do not exist yet.
2. **An `ensure_*` function** in `backend/app/main.py` (53 of them) or, since 2026-11-09, in an importable module under `backend/app/db_migrations/` that `main.py` calls for databases that already exist. Each guards before it changes anything (an `information_schema` lookup, `IF NOT EXISTS` or `WHERE NOT EXISTS`), then runs `ALTER TABLE ... ADD COLUMN`, an enum change or an insert of seed rows (for example `ensure_report_status_rows`), so it is safe to run on every start. They are called in sequence when `main.py` is imported. The ones read here use `information_schema` and `DUAL`, which are MySQL.
3. **The schema snapshot** for new installs: `Database3.4_subdivision.sql` and its `.txt` copy, updated by hand.
4. **`DATABASE_SCHEMA.md`**, regenerated from the database after the change.

Each change also gets a change record under `docs/05-operations/agents/feature-updates/`.

## Case workflow migration (2026-11-09)

`run_case_alignment(engine, strict=False)` in `backend/app/db_migrations/case_alignment.py` runs these steps, each in its own transaction on a connection that gives up on a metadata lock after 60 seconds (MySQL's own default is a year, which would hang start-up). A failing step does not stop the others; what happens next is under "When a step fails":

1. creates `case_followups`, `case_contact_logs`, `case_links` and `ownership_claims` from the models when missing;
2. adds 28 columns to `reports` (the 27 of 2026-11-09 and, since 2026-11-11, `pet_snapshot`, a nullable JSON column) in **one** `ALTER TABLE` (MySQL 8 keeps only 64 "instant" column additions per table, and one statement counts once), an index on `case_status`, five foreign keys to `users`, and appends Bird, Small mammal, Reptile, Livestock, Wildlife and Other to the `animal_type` ENUM (members added at the end, so MySQL changes it in place);
3. fills `reports.case_status` and `identity_status` from what each row already says (only where still empty);
4. adds 11 columns to `barangay_referrals` and `status_after` to `barangay_referral_updates`, makes `barangay_id` nullable, and replaces the one-referral-per-report unique key with a plain index (the plain index is created first because it backs the foreign key; the unique key is found by what it covers, not by its name); then fills `org_type`, `org_name` and `referral_status` for existing rows;
5. adds 5 columns to `owner_warnings` and `alert_type` to `lost_pet_alerts` (existing rows read `lost_pet`);
6. adds the six categories by name when missing.

It never drops a table or a column, never rewrites a stored value, and a second run does nothing (`test_case_alignment_migrations.py` checks both on a legacy-shaped database with historical rows, and checks the MySQL statements against a fake MySQL that holds state: ordering, batching, no destructive statement, zero DDL on the second run). **What the tests could not run:** the MySQL-only statements against a real MySQL server, and the migration against the real data.

### When a step fails

Every other step still runs, a failed step is tried **once more** (another process starting at the same moment may have done the work; every step is safe to repeat), and then the schema is **verified** against what the code needs (`check_case_schema`, read-only). The verified schema, not the step's exit status, decides:

| Status | Meaning | At start-up |
|---|---|---|
| `ok` | everything the code needs is there | starts; one INFO line |
| `degraded` | something the code can live without is missing: the `case_status` index, a foreign key, the wider `animal_type` list, the unique key still on `barangay_referrals.report_id`, `barangay_id` still required, a category | starts; one ERROR line per gap, each saying what it costs |
| `failed` | a table or column the models read is missing, or the schema cannot be inspected | **does not start**: `main.py` calls `run_case_alignment(engine, strict=True)`, which raises `CaseAlignmentError` naming what is missing and the step that failed |

If the application stops with `CaseAlignmentError`: read the message, fix the cause (usually the database user lacks `ALTER` or `CREATE` rights, or another session holds a lock on `reports` or `barangay_referrals`), and start again. Nothing was dropped or rewritten, and the migration is safe to repeat. The database error number is in the message (`error 1142` is a missing privilege, `error 1205` a lock timeout). To apply it by hand, run `run_case_alignment(engine)` from a Python shell on a machine whose `DATABASE_URL` points at the database; it logs what it changed. Taking a backup first is still the rule.

Not covered: two application processes creating the same new table at the same moment can make one of them fail inside the older `Base.metadata.create_all` call in `main.py` (MySQL error 1050). Restarting that process is the remedy. The case workflow steps recover from the same race on their own.

### Reading a database without any risk

The application does the check below at every start. To look yourself, or to ask what the next start would conclude, make the session read-only on the **server**, so no mistake can write: send `SET SESSION TRANSACTION READ ONLY` first, confirm `SELECT @@session.transaction_read_only` is `1`, and send only `SELECT` and `SHOW`. MySQL then refuses every `INSERT`, `UPDATE`, `DELETE` and DDL statement on a permanent table in that session. To run the same verification the application runs, without starting it (run from `backend/`; `URL` is the database to inspect):

```python
import os, tempfile
os.environ["DATABASE_URL"] = "sqlite:///" + os.path.join(tempfile.mkdtemp(), "unused.db")   # the app's own engine must never be the one you inspect
from sqlalchemy import create_engine, text
from app.db_migrations.case_alignment import check_case_schema
live = create_engine(URL, pool_size=1, max_overflow=0, connect_args={"init_command": "SET SESSION TRANSACTION READ ONLY"})
with live.connect() as c:
    assert c.execute(text("SELECT @@session.transaction_read_only")).scalar() == 1
print(check_case_schema(live))      # {"critical": [], "degraded": []}: the next start says "ok"
```

**Check it by hand (read-only):**

```sql
SELECT COLUMN_NAME FROM information_schema.COLUMNS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'reports' AND COLUMN_NAME IN ('case_status','incident_verification','closure_disposition','is_sensitive');
SELECT case_status, COUNT(*) FROM reports GROUP BY case_status;      -- no NULLs once the backfill has run
SHOW CREATE TABLE barangay_referrals;                                  -- barangay_id NULL, KEY ix_barangay_referrals_report_id, no UNIQUE on report_id
SHOW COLUMNS FROM reports LIKE 'animal_type';                         -- enum(...,'Bird','Small mammal','Reptile','Livestock','Wildlife','Other')
SELECT category_id, category_name FROM report_categories;              -- the six categories, the old ones unchanged
```

**Taking it back is not recommended and is not automatic.** The application code now expects these columns, and `main.py` applies the migration again at the next start. To return to the 2026-11-08 schema, revert the code first, take a backup, then drop the four new tables and the new columns listed in `DATABASE_SCHEMA.md` (rows marked new), restore the `animal_type` ENUM and the unique key on `barangay_referrals.report_id` (only possible while no case has two referrals), and make `barangay_referrals.barangay_id` NOT NULL again (only possible while no referral has an empty one). The five added categories can stay.

## Where database refactoring connects

- Make the change in the model, add its `ensure_*` function to the start-up sequence in `main.py` following the pattern above, and update the snapshot and `DATABASE_SCHEMA.md`.
- Use the dump to compare columns against the models and the snapshot, not as the place to make changes.

### First Subdivision Leader created (2026-11-10, one-time local bootstrap)

The rebuilt database had no user, and the application can create a Subdivision Leader only through an Admin (role 4 is reserved and none exists). The developer therefore approved a **one-time local bootstrap of the first Leader**, instead of seeding an Admin or a default credential or adding an account-management workflow to the application.

- **The tool.** `C:\StraySafe-db-backups\tools\bootstrap_first_leader.py`, next to the backup: local, outside the repository and OneDrive, imported by nothing and never run by the backend's start-up. The developer runs it in their own terminal (`<repository>\.venv\Scripts\python.exe C:\StraySafe-db-backups\tools\bootstrap_first_leader.py`). It refuses to run through a pipe or a chat tool, from an SSH session, or with any argument. It is a local convenience and is not stored in the repository: on any other database the supported route to a Leader is still an Admin.
- **What it asks and checks.** Name, e-mail address, an optional phone number and an optional position (and the subdivision, only if there is more than one), then a password typed twice and never shown. The password goes through the application's own policy (`enforce_password_policy`: 12 to 128 characters with an upper-case letter, a lower-case letter, a number and a special character), bcrypt's 72-byte limit and a refusal of the demo passwords found in the repository snapshot, and is hashed with the application's own `get_password_hash`. A typed `CREATE` is required at the end.
- **What it writes.** Exactly one row in `users`, through the application's `User` model and `AdminUserCreate` schema: role 2, linked to the existing subdivision, status Active, verified, not a head officer, no `barangay_id`, `password_changed_at` set, the e-mail address stored stripped and lower-case. That is the shape of a Leader that an Admin provisioned and who has already set a password. Nothing else is written (no audit-log row: nobody is signed in and the tool is not part of the application); the schema and the reference data are not touched.
